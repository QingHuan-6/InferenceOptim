# 毕设评价指标约定

状态：已确定的实验设计，版本 V1.1，日期 2026-11-13。
本文件确定指标与统计口径，不表示所有统计功能已经实现或验收目标已经达到。
适用初始硬件为单张 RTX 4090；论文依据见 [评测文献记录](benchmark_references.md)。

## 第一阶段的正式指标

第一阶段评价串行单请求的普通解码和后续投机解码，以解码加速比为主结果，
同时报告端到端收益、响应延迟、显存及正确性。暂不宣称系统并发吞吐提升。

设请求起点为 0，输出 token 数为 N，实际可用时间为 t₁…tₙ，请求结束时间为 E。
时间线保存秒，论文表格展示 ms、ms/token，内存展示 GiB（字节除以 2³⁰）。

| 指标 | 固定定义 | 统计与用途 | 当前状态 |
| --- | --- | --- | --- |
| 解码耗时 D | tₙ−t₁，首 token 可用至最后一个输出 token 可用；N<2 时缺失 | 秒；均值、P50；与 TTFT、E2E 分别报告 | 已计算与汇总 |
| 平均 TPOT | (tₙ−t₁)/(N−1)，排除首 token；N<2 时缺失 | 逐请求求值，主表报告均值与 P50；主性能指标的基础量 | 已计算 |
| 解码加速比 | 同一负载基线平均 D / 优化平均 D | 固定输出长度的主结果；按场景、输入长度档报告；不以各请求加速比的平均值代替 | compare 已按场景实现；输入长度分桶待实现 |
| 端到端延迟 E2E | E，含请求内分词、传输和最终文本解码，不含模型加载/下载 | 报告均值、P50，并用基线平均 E / 优化平均 E 计算端到端加速比 | 已计算，compare 已实现 |
| TTFT | t₁；N=0 时缺失 | 报告均值、P50；用于检查解码改进是否增加首次响应开销 | 已计算 |
| 单请求解码速率 | (N−1)/(tₙ−t₁) | token/s，辅助展示；每请求 TPOT 的倒数，不能把均值倒数误当作倒数均值 | 已计算 |
| 峰值设备显存 | 每请求 PyTorch max_memory_allocated，包含常驻权重 | 主表使用本组所有有效请求峰值的最大值；不等同于 nvidia-smi 或 reserved memory | 已记录并汇总最大值 |
| 贪心序列完全匹配率 | 相同输入、模型、模板和停止策略下，长度与全部输出 token ID 相同的请求数 / 有效配对请求数 | 比例及匹配数/配对数；无配对时缺失；分叉位置和各路径重复稳定性另报 | verify 已保留逐条证据；比例汇总待实现 |

TPOT 和端到端加速比必须同时报告。不得把 TTFT 变化忽略后，将解码加速比描述成整体加速比。
单请求解码速率不是多请求的系统吞吐量。
V1.1 将主加速比明确为解码耗时之比；固定 N 时，它与平均 TPOT 之比相同。
自然 EOS 下长度可能不同，另报实际长度、解码速率和任务质量，不把更早停止直接当作算法提速。
指标方案不改变旧字段含义或现有 verify 的严格 passed 判定。
后续原生基线实现以 schema=2 兼容新增 decode_elapsed_s、长度统计和峰值汇总，旧结果不自动补字段。

## 第二阶段的投机机理指标

下列指标用于解释加速原因，不能取代真实耗时和加速比。当前均待投机后端实现。

| 指标 | 定义及边界 |
| --- | --- |
| 草稿 token 接受率 | 所有轮次被接受的草稿 token 总数 / 实际提议的草稿 token 总数；不包含目标模型补发或奖励 token；分母为 0 时缺失 |
| 每轮有效推进 token 数 | 最终实际输出 token 总数 / 验证轮数；包含目标模型补发 token，尾部超过输出上限的 token 不计入推进；验证轮数为 0 时缺失 |
| 草稿/验证/其他开销 | 每请求分别累计实际草稿生成、目标验证、其他处理耗时；报告均值，保留原始分解；未来异步重叠时另报重叠量，不能强行相加 |

接受率按总计数之比汇总，不平均各轮百分比；每轮推进按总输出数/总验证轮数汇总。
草稿/验证/其他耗时单位为秒，另可展示 ms；未测量的分项为 null，不从总时间臆测。
DSpark 默认接受长度包含 bonus token，本项目对应“每轮有效推进”；草稿接受率明确排除 bonus。
同时记录实际送检草稿数，以区分动态验证长度与固定草稿长度。
只能用实际保留的输出计算有效速度，不采用“所有草稿全部接受”的假设吞吐。

真实计算工作不能因输出截断而从耗时中扣除；丢弃的尾部草稿和验证仍计入成本。
树式草稿若接入，需另行说明候选数与接受路径口径，不能直接与线性草稿接受率混比。

## 第三阶段的并发服务指标

这些是调度与双 SLO 扩展阶段的指标，当前串行 runner 不支持其测量。

| 指标 | 固定口径 |
| --- | --- |
| 请求吞吐量 | 测试窗口内成功完成请求数 / 窗口秒数，requests/s；并列报告提交数、失败数、未完成数 |
| 系统输出吞吐量 | 同一窗口内成功完成请求的全部输出 token 数（包含首 token）/ 窗口秒数，token/s |
| 双 SLO 达标率 | 同时满足 TTFT≤预设阈值、请求平均 TPOT≤预设阈值的请求数 / 测量期提交请求数；失败、超时、未完成均为不达标 |
| SLO 约束下的服务容量 | 保持双 SLO 达标率≥99% 时最大可持续请求到达率，requests/s；必须给出到达过程、持续时间和每档请求数 |
| P99 请求 TPOT | 对每请求平均 TPOT 求 P99，对应任务书尾时延约束 |
| P99 TBT | 对所有有效请求连续 token 间隔 tᵢ−tᵢ₋₁ 求 P99，另报各场景结果；不能与上一行互换 |

测量窗口从第一条测量请求提交到全部测量请求结束或达到预先固定的超时边界，
包含排空时间，不包含预热。不同方法使用相同输入、到达轨迹、超时和窗口规则。
TTFT、TPOT 阈值需在基线预实验后书面固定，测试优化方法时不再调整。
99% 是本项目确定的达标率目标，不是所有论文统一采用的常数。
N<2 的完成请求不能进入 TPOT 双 SLO 正式负载；在执行前固定最小输出规则，不事后删样本。

## 输出质量与量化扩展

- 正确性分成实现逻辑、数值差异、生成一致性和任务质量四类证据，不用一个标志代替全部结论。
  verify 的严格 token/重复一致性失败仍记失败；允许继续收集标注“待验证”的性能基线，
  不将失败改为通过，也不据此声明无损收益。
- 真实模型序列不一致需保留首个分叉、固定前缀 logits 诊断及精度对照。
  数值差异可能解释分叉，但必须有证据；同一路径重复漂移单独定位，不能直接归因于 BF16。
  有限样本 100% 一致不能代替算法证明，任务成绩接近也不能证明分布等价。
- 数学质量使用 GSM8K 答案正确率，固定答案提取与规范化规则；单位为比例，按题目等权。
  空输出、格式错误和超时计错误，报告有效评测题数；未运行评分器时为 null。
- 正式代码质量使用 HumanEval pass@1（单次生成通过功能测试的比例），
  评分器、模板及提取规则需固定；当前只提取 prompt 测性能，尚未实现此评分。
  单位为比例，按题目等权；生成失败或未通过测试计失败；评分器执行故障须单列，
  未完成的质量评测不能当作完整 pass@1，未测时为 null。
- JSON 扩展分别报告解析成功率、Schema 合规率和任务正确率；前两项不能代替语义正确。
  评测集和判定规则确定后实现，当前不宣称已覆盖。
- 若做有损量化，报告质量相对下降率和绝对百分点变化；前者采用
  (基线分数−量化分数)/基线分数，基线分数为 0 时缺失，不能用缺失值判定通过。
- 采样分布等价性不要求相同 seed 下输出文本必然一致。任务书 KL<1e-2 保留为
  采样扩展的附加目标；需先规定同前缀、同词表下的概率分布、KL 方向与聚合方式，
  不能从若干输出文本或贪心 token 匹配推算该 KL。

## 正式统计和对照规则

1. 初始性能对照固定 batch=1、raw greedy、输出 128 token（忽略 EOS）；
   自然 EOS 停止另组评价，不能将两种停止策略混合计算加速比。
2. 固定模型/分词器 revision、输入与模板、精度、attention、停止策略和计时模式。
   不同方法按 prompt ID 配对，并交错运行，避免设备状态随时间变化造成系统偏差。
3. 每配置先预热 5 次；每条输入正式重复至少 3 次。预热不纳入统计。
   同一输入先取重复测量均值，再对输入等权求主表均值；分位数以请求测量值求取。
4. 主结果按数据集/场景及输入长度档分开报告，不用不同组成比例混出单个“总加速比”。
   报告样本数、输入输出实际长度分布、排除规则和失败数；禁止只展示最快样本。
5. 加速比的置信区间按 prompt ID 配对重采样，保留每条输入的重复测量关系；
   不能把重复运行当成独立问题样本。compare 已实现提示级配对 bootstrap（1000次，seed=42），
   单场景不足2题时区间为null；工具不代替交错执行或输入长度分桶。
6. 缺失值使用 null，不能替换为 0。失败请求不纳入成功请求延迟均值，但必须报告；
   存在未解释差异时可以报告探索性性能，不能标为通过严格等价验收或已证明无损。
   有损方法需明确标注，并报告质量与速度的取舍，不能套用无损结论。
7. P99 是分位数而非“99% 成功率”。小样本结果不作尾时延结论，服务实验另行报告
   请求数、token 间隔数、负载和完整分布，不只提供 P99 单点。

## 与任务书目标的对应

- 单请求目标：同一负载的解码加速比≥1.8×；代码、结构化输出分别≥1.4×。
- 服务目标：同一双 SLO 下服务容量≥基线 2×；P99 请求 TPOT≤基线 1.1×。
- 量化扩展目标：4 bit 条件下质量相对下降≤1%，峰值显存下降≥50%；
  32K 以上上下文是额外测试条件，不代表默认 4090 配置已支持。
- 输出等价和 KL 条件按上述适用范围分别验证，不互相替代。

这些是待验证的研究目标，不能预先保证全部实现。当前阶段首先完成真实设备基线和正确性验证。
